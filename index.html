Scoring system

A review queue, not a black box.

Tailor Layer uses deterministic, inspectable rules over the artifact text. A score makes the first review decision faster; the evidence and suggested change remain the important part.

01 · Select

Public repositories are mapped for agent-facing instructions, manifests, configuration, source files, and scripts. Unsupported binary and build output are skipped.

02 · Match

Rules look for concrete behavior such as pipe-to-shell execution, hidden instructions, tool-order overrides, sensitive credential stores, broad permissions, and new outbound endpoints.

03 · Explain

Each match records the source file, line, excerpt, why it matters, and the safer edit to make before an agent uses it.

CRITICAL · −42

Remote execution or hidden behavior. The score is capped at 20: block installation until the behavior changes.

HIGH · −24

Authority override, credential-store access, hard-coded secrets, or host-impacting commands. The score is capped at 55: remediate or make an explicit decision.

MEDIUM · −7

Unpinned package execution or broad shell authority. These require a production review but do not automatically block sandbox evaluation.

INFO · 0

Declared endpoint or boundary. It does not lower the score; it gives the integrator an outbound-data review task.

Evidence is de-duplicated

Ten mentions of the same rule category do not produce ten penalties. The score reflects distinct kinds of risk; each file occurrence remains visible in the review center.

Links lead to context

For repository scans, every finding points to the exact GitHub file and line. Suggested changes link back to the evidence they address.

Use score with scope

Check that new permissions, commands, package versions, and endpoints are necessary for the claimed agent task. Then test in a sandbox with least-privilege credentials.

What this catches

Known static patterns in the text and source files that Tailor Layer can read. It is designed to focus human attention before installation.

What it cannot prove

Runtime behavior, dependencies fetched later, compromised releases, private files, server-side responses, or a tool’s intent. Treat a clean result as “no matched patterns,” never as a security guarantee.

What to do next

Pin the reviewed version, isolate the first run, verify outbound hosts, and grant only the authority required for the task.
